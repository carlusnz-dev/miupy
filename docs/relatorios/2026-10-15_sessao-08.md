## Fluidez com GPU (o problema principal da sessão)

**Sintoma (autor):** com "Aceleração de hardware: Ativada", animações e hover andam "aos degraus"
(sensação de ~15 fps) e às vezes um feixe preto cruza a tela. Em `localhost:1420` no navegador
fica perfeito. Segundo o autor, no começo do projeto não havia isso.

**Máquina:** Arch, Hyprland 0.56.2, notebook **híbrido** — Intel i915 (`card2`/`renderD129`, liga
o painel `eDP-1`) + NVIDIA 615.78.08 (`card1`/`renderD128`); painel 1920×1080 **144 Hz**, escala
**1,2**; WebKitGTK 2.54.1; o ambiente do autor exporta `__NV_PRIME_RENDER_OFFLOAD=1`,
`__GLX_VENDOR_LIBRARY_NAME=nvidia` e `__VK_LAYER_NV_optimus=NVIDIA_only` (tudo vai para a NVIDIA).

**Como foi medido:** `WEBKIT_INSPECTOR_HTTP_SERVER=127.0.0.1:9333` e um script Node que fala o
protocolo do inspetor (`Target.sendMessageToTarget` → `Runtime.evaluate`, `Timeline`, `Memory`,
`LayerTree`) — o console do WebKitGTK não serve para isso. `top -H` por thread. `eu-stack` é
barrado (`ptrace_scope=1`). Scripts fora do repositório (scratchpad da sessão).

| Achado | Evidência | Situação |
|---|---|---|
| Mesh animado redesenhava a tela inteira a cada quadro | 4 animações infinitas; CPU janela ~37% e WebKit ~40% → 4,4% e 2,4% com elas pausadas | **corrigido** no #62: mesh estático, só transição de cor |
| A pausa do mesh nunca funcionou | `animation:` inline em cada `.mesh-layer` vence `.mesh.paused` | **corrigido** no #62 |
| A página gera quadros direito | rAF ~60 fps em repouso, com mesh e rolando; hover compõe ~61×/s com 2 pinturas (acelerado, inclusive `linear()`) | não é o código da interface |
| WebKit preso perto de 60 fps num painel de 144 Hz | rAF 60 (NVIDIA) / 72 (Intel); preferência interna `PreferPageRenderingUpdatesNear60FPS` | desligada no `fix/webkit-quadros` via `webkit_settings_set_feature_enabled` (rAF chega a ~105–144) |
| GPU em qualquer variante engasga | NVIDIA DMABUF; Intel DMABUF (`env -u` das variáveis PRIME + `__EGL_VENDOR_LIBRARY_FILENAMES=…50_mesa.json` + `WEBKIT_WEB_RENDER_DEVICE_FILE=/dev/dri/renderD129`); `WEBKIT_DMABUF_RENDERER_FORCE_SHM=1`; sem teto; tela a 60 Hz | **não resolvido** — autor: "mesmo erro" em todas |
| **Software fica perfeito** | `MIUPY_GPU=off` (`WEBKIT_DISABLE_DMABUF_RENDERER=1`), com teto de 60 fps | autor: "deu certo, está perfeito" |
| Software sem o teto de 60 fps | p50 7 ms, mas p95 30–57 ms, pior 92 ms; rolagem ~40 fps | **sem resposta do autor** ao encerrar |

Memória em repouso no Início (app real): JS 12,6 MB; imagens decodificadas 62,6 MB (capas grandes
para miniaturas de 48 px — candidato a miniatura); 56 camadas compostas ≈ 30 MB (com o mesh
antigo); ~900 nós no DOM. Não é a causa do engasgo.

**Hipóteses que restam (não testadas):** o compositor (`hyprctl keyword misc:vfr false`,
`render:direct_scanout 0` — sugeridos ao autor, sem retorno); a apresentação do GTK3 com escala
fracionária 1,2; e o fato de o autor não ter estes engasgos "no início" — se a regressão for no
app, um bisect por tags (v0.1.x → v0.3.0) com GPU ligada diria o commit.

**Fontes consultadas:** [tauri-explorer #1057](https://github.com/xnmp/tauri-explorer/issues/1057)
(mesma combinação Hyprland + NVIDIA + WebKitGTK 2.54.1; SHM baixou a rolagem de 44–68 ms para
17 ms lá), [Tauri — Linux graphics](https://v2.tauri.app/develop/debug/linux-graphics/),
[wry #617](https://github.com/tauri-apps/wry/issues/617),
[coolapk-desktop #53](https://github.com/daimiaopeng/coolapk-desktop/issues/53) (144 Hz → 72 fps).
